Question

Can Claude Code replace n8n for automation/workflows?

n8n

When the workflow is a known graph.

These triggers, those steps, that destination. And when non-technical teammates need to inspect or own the flow visually.

  • Triggers · steps · destination
  • Inspect or own the flow visually
  • Non-technical teammates
Claude Code

When the work involves judgment in the middle.

Read this, decide what it is, route accordingly. An ecosystem running agentic loops — Plan → Do → Check → Repeat.

  • The right shape when "what to do next" is itself the work
  • Plan → Do → Check → Repeat
  • Plenty of teams run both

How does Claude Code compare with Cursor — and does Cursor have a CLAUDE.md equivalent?

Cursor

Lives in the editor. Accelerates the code you're writing.

  • Different surfaces
  • AGENTS.md is Cursor's CLAUDE.md analog
  • Older: .cursorrules — same idea, different filename
Claude Code

Lives in the terminal / IDE as an app / independent app.

  • Tends to take on longer tasks
  • Full features, refactors, multi-step jobs
  • Most people don't pick a side — they reach for whichever fits the moment

Same family, different jobs. The mental model transfers across CLIs (Gemini's GEMINI.md, etc.) — the specifics don't.

Terminal / IDE
Claude Code

Built for a wider surface: codebase work, automation, agent teams, scheduled jobs. For builders shipping products.

Desktop app
Claude Desktop

The visual chat interface with local file access and easier MCP setup. If the output is a conversation, Desktop fits.

Research preview · Jan 2026

Anthropic's knowledge-work agent. Builds spreadsheets, decks, reports; connects to Google Drive, Gmail, DocuSign. For office workflows.

Local · personal
OpenClaw

More about personal automation across devices and runs locally. For personal/system automation. They aim at different jobs.

Full-stack builder
Antigravity

Built for full-stack app generation with high control over the build. Common pattern: prototype the app in Antigravity, then bring it into Claude Code when the work shifts from "build the thing" to "operate the thing."

Gemini CLI

Uses GEMINI.md, has its own extension model, and structures things differently. The mental model transfers; the specifics don't.

Workflow graphs
n8n

Shines when the workflow is a known graph: these triggers, those steps, that destination. Plenty of teams run both.

In-editor
Cursor

Question

Do you need a separate CLAUDE.md per project? And do these files cost tokens?

Project CLAUDE.md

The brain of your project.

  • Loaded every session
  • Carrying memory, glossary, definitions, and architecture notes
  • Specific to this codebase
  • A project-level CLAUDE.md is the standard pattern
Global ~/.claude/CLAUDE.md

Optional.

  • Useful if you find yourself repeating the same preferences across repos
  • Plenty of people only use the project file and never feel a gap
  • Start there — add the global one if the same instructions keep piling up in three different projects
⚠ Token reality

A bloated CLAUDE.md is the most common own-goal.

CLAUDE.md is in context on every turn — it costs money on every turn and dilutes attention. Skills are lighter. Only their name and description sit in context, and the body loads only when the skill fires. A handful of well-scoped skills is cheap; a hundred poorly-scoped ones become noise. Skills aren't a free lunch, just a smaller bill.

Is "CLAUDE.md = what, SKILL.md = how" the right mental model?

Fair shorthand. The cleaner cut is when.

CLAUDE.md

WHAT — project memory.

What's true about this codebase, always.

  • Loaded every session
  • Memory, glossary, definitions, architecture
  • Always-on context
SKILL.md

HOW — step-by-step guidance.

How to do a particular kind of work when it shows up.

  • Step-by-step guidance for a specific task
  • Loads only when its description matches the task at hand
  • Lazy-loaded body

Question

How are skills different from tools — and from subagents?

= Capabilities
Tools

Tools are capabilities: Read, Bash, WebFetch. Claude calls them and code runs.

= Recipes for using tools
Skills

Reusable instruction packs that tell Claude how to use those capabilities in a particular order to accomplish a particular thing. A saved prompt with superpowers — turning 1000 words of instructions into a single slash command.

= Specialists
Subagents

A specialized co-worker with its own context, its own tool access, and its own model preference. Returns a summary rather than a step-by-step.

Reach for a skill when you want to stay in the loop. Reach for a subagent when the work is bulky, parallelizable, or independent enough that a summary is the only part you actually need.

Question

How does Claude pick a skill — and how do I trust one I downloaded?

Picking

The description field is the trigger.

  • Claude reads each installed skill's description and auto-invokes the one that matches the task
  • Vague descriptions don't fire, specific ones do
  • Or call a skill explicitly with /skill-name
  • Not documentation — the matching surface, and the part most people underinvest in
Bundling

Separate is the more common recommendation.

  • A bundled "do everything" skill ends up with a description so broad it triggers either always or never
  • Match the shape of the skill to the shape of the trigger
  • If two capabilities are genuinely always used together, one skill is fine
⚠ Safety

Read it like you'd read a shell script before piping it to bash.

Two real risks: prompt injection that nudges Claude into something you didn't ask for, and Bash commands that touch your system. Open the SKILL.md, check what tools it declares, and look at any scripts it ships. Claude Code is permission-gated by default — but the first risk only gets caught by you reading the skill. Treat skills from strangers the way you'd treat any third-party code.

Each as a markdown file with frontmatter for system prompt, tool access, and model preference.

Question

Where do tool access and model routing live?

Permissions · two layers

Two layers.

  • Project-wide permissions live in settings.json
  • Subagents additionally declare their allowed tools in frontmatter — a narrower slice than the main session has
  • CLAUDE.md and skills don't grant anything — they instruct behavior within permissions you've already drawn

Permission is harness-level.
Instruction is conversation-level.

Model routing

Each subagent declares a model preference in its frontmatter — that's the routing surface.

  • Cheap models (Haiku) for narrow, high-volume tasks like classifiers
  • Capable models (Opus) for reasoning-heavy work
  • The Plan → Do → Check loop: "powered by models that reason and tools that act"
  • Routing right is mostly about matching cost, latency, and quality to what each step actually needs

Question

What exactly is a "harness"?

The engine that turns the model from a text predictor into a working agent. The model can only produce text; the harness reads that text, runs the actions it implies, shows the model what happened, and loops until the work is done.

The model thinks.
The harness does.

01
The loop

Keeps Plan → Do → Check → Repeat running until the task is complete.

02
Tools

Exposes file edits, terminal commands, search, and web access as things the model can call.

03
Memory

Keeps context coherent across long sessions.

04
Guardrails

The model never touches your system directly; every action flows through an allow-list, and risky moves require your approval.

Together they're an agent.

Question

Why hooks for control measures, instead of just defining them in a skill?

Different guarantees.

Skills

Instructions Claude reads.

  • Claude decides whether to follow them
  • Usually does, but not always
  • If guidance is enough, a skill is lighter
Hooks

The deterministic control layer.

  • Scripts that run every time on the events you specify (PreToolUse, PostToolUse, Stop), with no exceptions
  • If you need a guarantee — blocking rm -rf, auto-formatting on edit, notifying on completion — you need a hook
  • Rigid by design, and rigidity has its place

Question

Can you fully automate topic → draft → publish on a schedule?

Yes. The pieces map directly to the rest of the deck.

The pipeline

Subagents do the work.

  • Research, drafting, formatting, and publishing
  • MCP connectors hit external systems — Substack, Drive, Gmail
  • Schedule recurring tasks: one of the listed Claude Code agent capabilities
⚠ The harder part

Earning the right to take yourself out of the loop.

  • Start semi-autonomous: agent drafts, you approve
  • Watch what goes wrong for a couple of weeks
  • Once the failure modes are predictable and acceptable, tighten the loop
