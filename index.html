Question

Can Claude Code replace n8n for automation/workflows?

n8n

When the workflow is a known graph.

These triggers, those steps, that destination. And when non-technical teammates need to inspect or own the flow visually.

  • Predictable, repeatable steps
  • Visual ownership matters
  • Shared with non-builders
Claude Code

When judgment lives in the middle.

Read this, decide what it is, route accordingly. An ecosystem running agentic loops — Plan → Do → Check → Repeat.

  • "What to do next" is the work
  • Branchy, judgment-heavy paths
  • Plenty of teams run both

Question

How does Claude Code compare with Cursor — and does Cursor have a CLAUDE.md equivalent?

Cursor

Lives in the editor. Accelerates the code you're writing.

  • Inline, line-by-line momentum
  • Best when you're already in the file
  • AGENTS.md is the CLAUDE.md analog (older: .cursorrules)
Claude Code

Lives in the terminal / IDE / standalone app. Takes longer tasks.

  • Full features, refactors, multi-step jobs
  • Reads codebases, runs commands, ships products
  • Most people don't pick a side — they reach for whichever fits the moment

Question

Antigravity, Desktop, Cowork, OpenClaw — how do they all fit?

Same family, different jobs. The mental model transfers across CLIs (Gemini's GEMINI.md, etc.) — the specifics don't.

Terminal / IDE
Claude Code

For builders shipping products. Reads codebases, writes files, runs commands, schedules jobs.

Desktop app
Claude Desktop

Visual chat with local file access and easy MCP setup. If the output is a conversation, Desktop fits.

Cloud · research preview
Claude Cowork

Anthropic's knowledge-work agent. Builds spreadsheets, decks, reports. Connects to Drive, Gmail, DocuSign.

Local / personal
OpenClaw

Personal automation across devices, runs locally. Different surface, different job — not a Cowork comparable.

Full-stack builder
Antigravity

High-control app generation. Pattern: prototype here, then move to Claude Code when you shift from build to operate.

CLI · Google
Gemini CLI

Uses GEMINI.md, its own extension model. Mental model transfers. Specifics don't.

Workflow graphs
n8n

Visual flows for known graphs. Triggers → steps → destination. Pairs well with Claude Code, not a substitute.

In-editor
Cursor

Editor-native acceleration on the code in front of you. AGENTS.md is its CLAUDE.md analog.

Question

Do you need a separate CLAUDE.md per project? And do these files cost tokens?

Project CLAUDE.md

The brain of your project.

  • Loaded every session
  • Carries memory, glossary, architecture
  • Specific to this codebase
  • Standard pattern — start here
Global ~/.claude/CLAUDE.md

Optional. Add if patterns repeat.

  • Useful when the same preferences pile up across 3+ repos
  • Plenty of people only use the project file
  • "Add it if you feel the gap"
⚠ Token reality

A bloated CLAUDE.md is the most common own-goal.

It's in context on every turn — costs money every turn and dilutes attention. Skills are lighter: only name + description sit in context; the body loads only when the skill fires. A handful of well-scoped skills is cheap. A hundred poorly-scoped ones become noise.

Question

Is "CLAUDE.md = what, SKILL.md = how" the right mental model?

Fair shorthand. The cleaner cut is when.

CLAUDE.md

WHAT — project memory.

What's true about this codebase, always. Loaded every session.

  • Glossary, conventions, architecture
  • Always-on context
  • Pays its tax every turn
SKILL.md

HOW — task-specific recipe.

Step-by-step guidance for one kind of work, when it shows up.

  • Loads only when its description matches
  • Body is lazy-loaded
  • Cheap to keep around

Question

How are skills different from tools — and from subagents?

= Capabilities
Tools

Read, Bash, WebFetch. Claude calls them and code runs. The verbs.

= Recipes
Skills

Reusable instruction packs that tell Claude how to use those capabilities, in order, to accomplish a thing. A saved prompt with superpowers — 1000 words → one slash command.

= Specialists
Subagents

Specialized co-workers with their own context, tool access, and model preference. Return a summary, not a step-by-step.

Skill: stay in the loop. Subagent: when a summary is the only part you need.

Question

How does Claude pick a skill — and how do I trust one I downloaded?

Picking

Description = the matching surface.

  • Claude reads each skill's description and auto-invokes the match
  • Vague descriptions don't fire. Specific ones do.
  • Or call explicitly: /skill-name
  • It's not documentation — it's the trigger
Bundling

Separate > one big "do everything."

  • Bundled skills end up with descriptions so broad they always trigger or never trigger
  • Match the skill's shape to the trigger's shape
  • Two capabilities always used together? Then one is fine.
⚠ Safety

Read it like a shell script before piping to bash.

Two real risks: prompt injection that nudges Claude into something you didn't ask for, and Bash commands that touch your system. Open the SKILL.md, check declared tools, look at any scripts. Claude Code is permission-gated by default — but the first risk only gets caught by you reading the skill.

Question

Where do tool access and model routing live?

Permissions · 2 layers

Project-wide vs per-subagent.

  • settings.json — project-wide allow-list
  • Subagent frontmatter — narrower slice for specialists
  • CLAUDE.md & skills don't grant — they instruct

Permission = harness-level.
Instruction = conversation-level.

Model routing

Per-agent model preference is the routing surface.

  • Haiku — narrow, high-volume tasks (classifiers)
  • Opus — reasoning-heavy work
  • Match cost · latency · quality to what each step needs
  • Plan → Do → Check is "models that reason + tools that act"

Question

Why hooks for control measures, instead of just defining them in a skill?

Different guarantees.

Skills

Instructions Claude reads.

  • Claude decides whether to follow them
  • Usually follows — not always
  • Lighter, conversational, easier to evolve
  • Good when guidance is enough
Hooks

Deterministic. Run every time.

  • Fire on PreToolUse, PostToolUse, Stop
  • No exceptions — block rm -rf, auto-format on edit, notify on completion
  • If you need a guarantee, you need a hook
  • Rigid by design — and rigidity has its place

Question

Can you fully automate topic → draft → publish on a schedule?

Yes. The pieces map directly to the rest of the deck.

The pipeline

Subagents do the work.

  • Research · Drafting · Formatting · Publishing
  • MCP connectors hit Substack, Drive, Gmail
  • Schedule recurring tasks — built-in capability
⚠ The hard part

Earn the right to take yourself out of the loop.

  • Start semi-autonomous: agent drafts, you approve
  • Watch what goes wrong for two weeks
  • Once failure modes are predictable & acceptable — tighten the loop
  • Trust is built, not declared
